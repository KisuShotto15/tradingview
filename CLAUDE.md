## Commands

```bash
npm run dev      # Next.js dev server (http://localhost:3000)
npm run build    # Production build (also runs the full TypeScript type-check)
npm run start    # Serve the production build
npm run lint     # ESLint (eslint.config.mjs, flat config)
npm test         # Unit tests (see below)
npm run test:watch
```

**Zustand `persist` in tests needs `window`, not just `localStorage`.** Zustand's default storage is `createJSONStorage(() => window.localStorage)` — `window`, not the bare global. With no `window` that accessor throws, `createJSONStorage` swallows it and returns `undefined`, and `persist` quietly takes its "storage unavailable" branch: the store still works, but it never writes, never rehydrates, and never runs `migrate` or `merge`. `test/polyfill.mjs` therefore defines a minimal `globalThis.window` carrying the stand-in storage, deliberately a bare object rather than an alias of `globalThis`, since code here branches on `typeof window === "undefined"` to detect SSR. Before that, every seeded-state test was really reading the store's *defaults*, so any assertion that happened to match a default passed for the wrong reason — which is how a broken palette migration got called proven. Two more things to know when writing one: rehydration is asynchronous even from a synchronous storage (`await` a macrotask before asserting), and the store module is cached per process, so **one rehydration test per file** — a second in the same file reuses the store the first one already hydrated.

**Tests** run on Node's built-in runner (`node --test`) with **no extra dependencies**. Node strips TypeScript natively; `test/register.mjs` (loaded via `--import`) registers a resolve hook for the `@/*` alias + extensionless imports and polyfills `localStorage` for Zustand `persist` stores. Assertions use a tiny Jest-style shim at [src/test-utils/expect.ts](src/test-utils/expect.ts) over `node:assert`. Tests live next to the code as `*.test.ts` and cover **pure logic only** (stores, indicators, drawing/alert math, sizing, formatting, symbol/exchange resolution) — no DOM/component rendering. Add a test: create `foo.test.ts` importing from `node:test` + `@/test-utils/expect`.

The `npm test` script bakes in the `src/**/*.test.ts` glob, so to scope a run, invoke node directly:

```bash
# One file
node --import ./test/register.mjs --disable-warning=MODULE_TYPELESS_PACKAGE_JSON \
  --test --test-isolation=none src/lib/trading/sizing.test.ts

# One test/suite by name, across the suite
node --import ./test/register.mjs --disable-warning=MODULE_TYPELESS_PACKAGE_JSON \
  --test --test-isolation=none --test-name-pattern="slInputToPrice" "src/**/*.test.ts"
```

Earlier versions of this file said `--test-isolation=none` was required for Zustand `persist`. It isn't: `test/register.mjs` is loaded per worker via `--import`, so every isolated process gets its own polyfilled `localStorage`, and the full suite passes without the flag. It has been dropped from the `test` scripts because it is a Node 24 flag and aborts outright on Node 22 (`node: bad option`) — which silently left `npm test` unrunnable.

**Install the dependencies and verify before claiming anything.** This file used to say the sandbox had no npm registry access; that is no longer true. `npm ci` works, and with it so do `npx tsc --noEmit`, `npm run build` and `npx eslint`. Skipping that check once let a type error — a `Record<IndicatorKey, string>` left incomplete by a new indicator key — sit on `master` across five commits, breaking every deploy while the code itself read as correct. `next build` needs `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` to get past prerendering `/_not-found`; any placeholder value works for a local check.

`next build` runs the full TypeScript type-check (`paths` alias `@/*` → `src/*`). Note **Next 16 removed ESLint from the build** — lint runs only via `npm run lint`, never blocks `next build`. The repo carries pre-existing `react-hooks` lint errors unrelated to most changes; don't treat a red `npm run lint` as a regression without checking whether your files are involved.

Requires `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` in `.env.local` (see `.env.example`). Without them, proxy auth and cloud sync fail. Market data needs no keys; private trading uses per-user keys entered in the UI.

## Architecture

Next.js 16 App Router, React 19, TypeScript, Tailwind 4 + shadcn/ui (Base UI primitives), Zustand for state, Supabase for auth + persistence, `lightweight-charts` v5 for rendering. **Everything client-side** except thin API routes.

### Symbol identity (read this before touching anything symbol-related)

A ticker string carries up to three pieces of meaning, and several bugs have come from conflating them:

- `BTCUSDT` — bare exchange symbol.
- `.P` suffix (`BTCUSDT.P`) — USDT-M **perpetual** rather than spot. `isPerp()`.
- `BYBIT:` prefix (`BYBIT:SOLUSDT.P`) — TradingView-style **exchange qualifier**, so a ticker listed on both venues can be charted from either. [src/lib/symbols/prefix.ts](src/lib/symbols/prefix.ts) is a dependency-free leaf module (imported by both low-level Binance helpers and the resolver, so it must not import them back).

`cleanSym()` in [src/lib/binance/rest.ts](src/lib/binance/rest.ts) strips **both** decorations to get the raw exchange symbol — that's what every exchange API call and every position/order match must use. `resolveSource()` decides which *data provider* serves the chart.

Consequence worth remembering: two different chart symbols (`SOLUSDT.P` and `BYBIT:SOLUSDT.P`) reduce to the same `cleanSym`, so matching an account position by symbol alone is not enough — see "Exchange gating" below.

### Data providers (multi-source)

`resolveSource(symbol)` in [src/lib/symbols/source.ts](src/lib/symbols/source.ts) classifies a ticker, and `fetchCandles()` in [src/lib/data/fetch.ts](src/lib/data/fetch.ts) dispatches on `src.kind`:

- **binance** — spot, or USDT-M perps, via `src/lib/binance/rest.ts` + live WebSocket (`ws.ts`).
- **bybit** — linear USDT perps via `src/lib/bybit/public.ts` (REST klines/tickers/instruments) + `src/lib/bybit/ws.ts` (live klines + tickers). Public data only; no credentials.
- **synthetic** — arithmetic expressions over symbols (spreads/dominance) via `src/lib/binance/synthetic.ts`.
- **yahoo / fred / coingecko** — stocks, indices, macro, market caps, proxied through `src/app/api/{yahoo,fred,coingecko}/route.ts` (these providers block CORS / need keys).

The symbol **catalog** ([src/lib/symbols/catalog.ts](src/lib/symbols/catalog.ts)) has a static half (curated stocks/indices/macro) and a **dynamic registry** populated at runtime: `useBybitSymbols` fetches Bybit's whole perp universe on app load and calls `registerDynamicEntries()` so those tickers resolve and appear in search. `resolveSource` also honours an explicit `BYBIT:` prefix *before* consulting the catalog, so a persisted Bybit symbol charts correctly right after a reload, before the registry has loaded.

When adding a data source: extend `ResolvedSource`, `SourceKind`, and the `switch` in both `resolveSource` and `fetchCandles`. Also give it a mark in `ExchangeLogo`'s `MARKS` map, or its search results fall back to Binance's badge.

Search results (`SymbolSelector.tsx`) render a `SymbolIcon` — the asset's coin icon with the venue's mark pinned to its corner — plus a long-form subtitle. Every `SearchRow` therefore carries a non-optional `description`: catalog entries use theirs, Binance rows get one composed from base/quote/contract type, and the string is matched by the search box too (typing "APPLE" finds AAPL). `CoinIcon`'s `remote` prop must be `false` for anything that isn't a coin — otherwise every stock/macro row fires a 404 at the crypto icon CDN before falling back to its letter avatar.

### Live data

Binance uses one multiplexed WebSocket (`src/lib/binance/ws.ts`) carrying `@kline_<interval>`, `@miniTicker` and `@bookTicker`. Bybit has its own (`src/lib/bybit/ws.ts`) exposing a deliberately **matching `subscribeKline` / `subscribeMiniTickers` shape**, so consumers pick a socket by source kind and otherwise treat them alike. Bybit requires a 20s heartbeat ping and sends ticker *deltas* (only changed fields), so its client retains last price/percent per topic, shared across every subscriber to that symbol. Both reconnect with exponential backoff. Non-crypto sources are REST-poll only.

`BybitWS.tickerSubs` fans a topic out to a **Set of listeners**, not a single callback — Bybit has no separate book-ticker stream, so `BuySellOverlay` reuses `subscribeMiniTickers` for its bid/ask quote on the currently-charted symbol, on top of whatever the watchlist already subscribed for that same symbol (Binance doesn't hit this: its `BuySellOverlay` quote uses `subscribeBookTicker`, a disjoint map). A single-entry map here silently drops whichever subscriber loses the race and orphans the topic when the other one unmounts — the watchlist row for the charted symbol goes stale until something forces a full resubscribe. Keep this fan-out shape if you touch this file; don't collapse it back to one listener per topic.

Bybit's public ticker stream pushes on every trade with no cap, unlike Binance's `@miniTicker`, which the exchange itself throttles to ~once/second — so a volatile Bybit row can emit several ticks a second. `Watchlist.tsx` and `WatchlistScreen.tsx` don't apply raw ticks straight to state; both route through `useBatchedTicks` ([src/hooks/useBatchedTicks.ts](src/hooks/useBatchedTicks.ts)), which coalesces same-symbol ticks arriving within a 150ms window into one `setRows`/`setFlash` flush. This is what keeps the price/flash animation from feeling "violent" compared to Binance rows — the feed itself isn't throttled, only the render rate is, the same trick TradingView's own UI uses. Any new live-tick consumer that renders a list (not a single quote) should go through this hook rather than calling `setState` straight from the WS callback.

**Staleness watchdog (why a chart used to freeze silently).** `onclose` is not guaranteed. A socket can be left half-open — laptop sleep, a network switch, a VPN dropping — with the TCP connection still nominally established and nothing ever arriving: the browser fires no event, `readyState` stays `OPEN`, and the chart simply stops updating with no error anywhere. The exponential-backoff reconnect never runs, because as far as the client is concerned nothing closed. Both clients therefore stamp `lastMsgAt` on **every** frame (a subscribe ack or a Bybit pong counts as proof of life) and run a 10s interval that force-closes the socket once it has been silent past `STALE_MS` ([src/lib/feed-status.ts](src/lib/feed-status.ts)) — which routes the failure back into the normal `onclose` → `scheduleReconnect` path. Bybit's 20s heartbeat is *not* this check: it only proved we were still sending, never that pongs still came back.

Each client publishes a `FeedStatus` (`connecting` / `live` / `down`) through a `FeedStatusEmitter`, which replays its current value to late subscribers so a component mounting mid-session is told the state immediately. Binance exposes it as `statusFor(symbol)`, not a single property — spot and futures are separate sockets, so "is the feed alive?" is only answerable per symbol. `useFeedStatus(symbol)` ([src/hooks/useFeedStatus.ts](src/hooks/useFeedStatus.ts)) picks the right emitter by source kind and is what `BottomPanel` renders; that badge used to be a hardcoded `Binance · Live` with a pulsing green dot, which lied about the venue on a Bybit chart and stayed green while the socket was dead — exactly when a user looks at it to find out why the price stopped moving.

**Neither the chart nor the watchlist may depend on the socket alone.** Both now fall back to REST when no tick has arrived for `TICK_SILENCE_MS` — the chart re-fetches a 3-bar tail every 5s through `mergeLiveCandles` (not `applyReplayCandles`, which re-sets every series from 1000 bars and is far too heavy to repeat on a timer), and the watchlists re-seed through the same `fetchTickers24h` / `fetchBybitTickers24h` call they already use once at mount. The watchlist was the worse of the two: it seeded once and every value after that came from the socket, so an open-but-mute socket froze every row at its opening price for as long as the tab stayed up, with no error and nothing to distinguish it from a flat market. This matters because a WebSocket can fail where plain HTTPS still works — a network that blocks or stalls `wss://`, a proxy, a captive portal — and in that case polling is the only thing that keeps the app usable.

**The socket watchdog cannot see a dead subscription.** `lastMsgAt` is stamped by *any* frame on the connection, and a Binance connection is shared — the chart's `@kline_<tf>` and the watchlist's `@miniTicker` streams ride the same socket. One ticking watchlist row keeps it fresh, so if the chart's own subscription stops delivering, the watchdog never fires and the badge goes on saying `Live` while the chart sits still. `markChartTick()` / `chartTickAgeMs()` ([src/lib/feed-status.ts](src/lib/feed-status.ts)) therefore track the charted symbol separately, written from the kline handler. Two things read it: the stale check force-rebuilds the subscription (a `feedNonce` in the load effect's deps, rate-limited by `RESUBSCRIBE_MIN_GAP_MS` so a genuinely dead market can't become a reconnect loop), and `useFeedStatus` exposes `stale`, which the badge shows as `No ticks`. The flag is kept separate from `FeedStatus` on purpose: the socket really is connected, so reporting it down would be wrong — but reporting `Live` is what made this undiagnosable from a screenshot.

**The backstop is a check on the data, not on the connection.** Both mechanisms above reason about the *socket*. `PriceChart` also runs a stale-bar check every 15s (and on `visibilitychange` / `focus` / `online`): if the newest bar's `barCloseTime` is more than 30s in the past and no successor has arrived, it refetches. That is the symptom the user actually sees, and it does not care which cause produced it — a half-open socket, a laptop waking from sleep, a dropped subscription, a reconnect that raced, or something not yet thought of. Prefer extending this check over enumerating new failure modes. It is restricted to the streaming sources: a REST-poll series (FRED updates at most daily) is *legitimately* older than its last bar's close and would refetch forever.

**That backstop must repair with a tail, not a reload — it cannot tell "a bar is missing" from "there is no newer bar".** A thin symbol, or any symbol between trades on a low timeframe, leaves the newest bar past its close indefinitely: the check goes on firing however many times it is repaired. Repairing with a 1000-bar refetch therefore meant a full `setData` on every series plus every indicator recomputed **every five seconds, forever** — which is what users reported as the chart rebuilding itself and flickering. The hole is bounded, though: candle history never changes, so the only bars that can be missing are the ones that closed since the newest one held. `missingBars` sizes a tail to exactly that, `tailConnects` checks it reaches back to what is drawn, `tailIsNoop` skips the splice when the exchange returned what we already have ([src/lib/chart/tail-repair.ts](src/lib/chart/tail-repair.ts), tested), and `mergeLiveCandles` applies it per bar. The 1000-bar refetch survives only for a gap too wide to splice (`MAX_SPLICE_BARS`) or a tail that does not connect, and then at most once per `FULL_REFETCH_MIN_GAP_MS`.

**A `feedNonce` bump re-runs the load effect, and the load effect must not treat it as a symbol change.** The effect opens by wiping every series so the previous symbol's candles never linger, then awaits a 1000-bar fetch, re-`setData`s everything and re-applies the saved viewport. On a resubscribe the symbol and timeframe are identical, so none of that is stale — and all of it is *visible*: the chart blanks for the length of the fetch and then snaps back, once a minute for as long as the stream stays quiet. `loadedKeyRef` holds the `symbol|timeframe` the effect last ran for; when it is unchanged the effect skips the wipe and the viewport restore and applies the fetch through `applyCandlesKeepingView`, whose `sameCandles` guard makes the usual case cost nothing. Anything else added to that effect's deps which is not data needs the same treatment.

**Reconnecting is not enough on its own.** A kline stream only sends updates from the moment of subscription, so a resubscribe resumes the *live* bar and leaves a hole where every bar that closed during the outage should be: the chart looks current while the last few minutes are missing, and `BarCountdown` counts down against a stale bar (it reads 00:00 and stays there). `PriceChart` subscribes to the feed status and refetches the full candle array on every non-live → live transition, applying it through the same `applyReplayCandles` the replay-exit path uses. A new consumer of a live feed that keeps its own history needs the same treatment.

### Indicators

**The RSI pane is built out of `BaselineSeries`, not an SVG overlay.** A baseline series fills between its data and a `baseValue` with a gradient, which covers both of the things that design needs: the soft red/green fill where the line pushes past 70/30 (`relativeGradient: true`, so the fade is anchored to the level crossed rather than to the pane's edges), and the flat 30–70 tint and extreme zones — those are fed a *constant* two-point series, so the "fill" renders as a plain rectangle. Doing it with series means the library handles pan, zoom and rescale; an overlay would have to recompute geometry on every one of those. The visible white line is drawn once by its own `LineSeries`: the two baseline series set `topLineColor`/`bottomLineColor` transparent, or the line would be painted three times in three colours. Creation order is z-order — backdrops, rails, fills, then lines.


**A sub-pane must exist before a series can be put in it.** `chart.addSeries(..., paneIndex)` does **not** create intermediate panes: an index beyond the last existing pane is silently clamped to the next free one. Inserting Stoch RSI into the ordering exposed this — MACD asked for pane 3 while only 0..1 existed, so its *first* series was clamped into pane 2 (creating it) and the other two then landed in 3, drawing the MACD line inside the Stoch RSI pane and blowing that pane's scale out to MACD's range. Every sub-pane effect calls `ensurePane(index)` first, which tops the chart up with `chart.addPane()`. Two related rules: each sub-pane effect must **tear its series down first** rather than `if (on && !ref) create`, since `addSeries` cannot move a series between panes and another study toggling shifts this one's index; and its dependency array must list **every** other sub-pane indicator, or it won't re-run when the index changes under it. The same ordering has to be mirrored in `panelIndexFor`, `indicatorPaneIdx`, the dblclick host lookup, the A/L button owner lookup, `resyncAutoScaleStates`, `seriesByPane` and the per-indicator log-scale effect — a key missing from any of those silently points that control at the wrong pane.

Pure TypeScript, computed client-side over the candle array on every update (`src/lib/indicators/`). `index.ts` has the primitives (`sma`, `ema` seeded with SMA, Wilder `rsi`, `macd`, `obv`); dedicated files hold the heavier custom studies (`adx.ts`, `squeeze.ts`, `vumanchu.ts`, `keylevels.ts`). Add a study: implement the calc, add its key to `IndicatorKey` + `IndicatorConfig`/`DEFAULT_CONFIG` in `chart-store.ts`, wire the toggle/settings dialog, and render its pane/overlay in `PriceChart.tsx`.

### State (Zustand stores, `src/lib/store/`)

**Adding a field to `IndicatorConfig` (or any nested settings object) needs no migration, but only because of `merge`.** Zustand's default merge is shallow *at the top level*: `config` is a single key, so a persisted `config` object replaces `DEFAULT_CONFIG` wholesale and any field added later arrives as `undefined` for every existing user. It fails silently, because `undefined` flows into a calculation or a chart option instead of throwing — `adxKeyLevel` hit this (patched per-key in the v4 migration), and the RSI zone levels shipped as `baseValue: { price: undefined }`, filling the whole pane red. `chart-store`'s `persist` config now supplies its own `merge` that deep-merges `config` under `DEFAULT_CONFIG`, and `use-cloud-sync` does the same with the Supabase row (`{ ...DEFAULT_CONFIG, ...settings.config }`) — the cloud copy is a whole object too, and would otherwise undo it on the next sign-in. Both paths are covered by `src/lib/store/config-merge.test.ts`. A *new nested object* (a new `fooStyle`) is not covered by that and still needs handling.


- `chart-store.ts` — symbol, timeframe, indicators + config, colors/visual settings, watchlists, chart type, right-sidebar tab/width, and the chart layout (`layout`, `panes`, `activePaneId` — see "Chart layouts" below). `persist`ed to localStorage.

**Changing a default that is persisted changes nothing on its own.** `chartColors` is written to localStorage *and* mirrored to Supabase, so editing `DEFAULT_CHART_COLORS` only reaches someone who has never run the app. A palette change needs a migration on **both** paths, and the cloud one is the subtle half: there is no version column on the row, and the cloud load runs *after* rehydration, so an unmigrated cloud copy restores the old colours on every sign-in. [src/lib/chart/candle-palette.ts](src/lib/chart/candle-palette.ts) therefore carries `CANDLE_PALETTE_VERSION`, which the cloud payload stamps into `visual_settings.candlePaletteVersion` and the loader compares against — making it one-shot. Unconditional there would be just as wrong in the other direction: it would overwrite whatever the user picked afterwards, every sign-in, and make the colour pickers useless.

The first attempt at this migration only rewrote a palette that still matched the previous default exactly, reasoning that a customised one should be left alone. That is the wrong default for a deliberate palette change: it reaches nobody who has ever opened the colour pickers — the people most likely to have asked for it. `applyCandlePalette` is unconditional, and the version marker is what keeps it from running twice.
- `drawings-store.ts` — all chart drawings (see below).
- `trading-store.ts` — exchange choice, API credentials, orders, positions, balance, order form.
- `alerts-store.ts` — standalone price/RSI/MACD alerts (see "Alerts" below). `persist`ed to localStorage only — unlike drawing-attached alerts, these do **not** sync to Supabase.
- `mobile-store.ts` — mobile sheet/screen navigation.

Watchlist flags live on the item (`flagColor`), and the palette is a dependency-free leaf module ([src/lib/watchlist/flags.ts](src/lib/watchlist/flags.ts)) precisely because `chart-store` needs `DEFAULT_FLAG_COLOR` to seed `lastFlagColor` while both watchlist components need the full list — the store must not import from a component. On desktop the flag is the row's **left** edge: a click toggles it using `lastFlagColor`, a right-click opens the colour picker (and updates `lastFlagColor`). The mark itself is `FlagPennant`, an inline SVG ribbon tag (rounded block, notch bitten out of the right side) rather than lucide's `Flag`, because a stroke-only glyph vanishes in a column barely wider than a scrollbar.
- `replay/replay-store.ts` — bar-replay cursor/playback (session-only, not persisted).

Note `trading-store` keeps **two** position lists: `positions` (scoped to the chart's current symbol, drives the chart overlay and order panel) and `allPositions` (every open position on the account, refreshed regardless of which symbol is charted — used by the watchlist to badge any row, and by the bottom "Trading Account" panel so it isn't blank just because a different symbol is on the chart). `allPositions` is the one actually fetched over the network (`fetchAllPositions`, unscoped `/api/trade/positions`); `positions` is derived from it client-side via `syncPositionsFromAll(symbol)` — no second request. `fetchPositions(symbol)` (a real, scoped fetch) still exists for one-off post-action refreshes (after placing/closing/modifying), just not inside the polling loop.

Cross-cutting hooks are mounted once in [src/components/providers.tsx](src/components/providers.tsx): `useCloudSync`, `useDrawingsSync`, `useKeyboardShortcuts`, `useTradingSync`, `useBybitSymbols`. `useTradingSync` polls `/api/trade/*` every 2s **while the tab is visible** — every route it hits is a real Node.js Vercel Function (Fluid compute bills these), so it pauses entirely on `visibilitychange`/`document.hidden` and resumes with an immediate refresh on foreground, rather than polling a backgrounded tab all day.

**`useTradingSync` is the only account poll in the app — keep it that way.** `PositionsPanel`, `TradeScreen` and `OrderPanel` all read `balance`/`orders`/`allPositions` straight off the store and render whatever the global poll last wrote. Each of those components used to run its *own* 5s interval over the same three endpoints, which silently multiplied the billed invocations (and, unlike `useTradingSync`, kept firing in a backgrounded tab). A panel needing fresher data is not a reason to add an interval — trigger a one-shot `syncAccount(symbol)` after a user action the way `placeOrder`/`closePosition` do.

Every refresh — the poll and the post-action ones alike — goes through **`syncAccount(symbol)`**, one request to `/api/trade/sync` that returns balance + orders + positions together, instead of three requests to the per-resource routes. On Vercel each of those three used to drag the auth proxy along too, so the batched route was a 6→2 cut in invocations per tick (now 3→1, since `/api/trade/` no longer runs the proxy — see "Route auth" below). The route returns `{ balance, orders, positions }` where each key is `{ data, error }`: the client applies only the slots that succeeded, so one failing read doesn't blank the panels fed by the other two. The single-resource routes still exist (`fetchBalance`/`fetchOrders`/`fetchPositions`) and share their implementation with the batched route via [src/lib/exchanges/account.ts](src/lib/exchanges/account.ts) — don't reimplement exchange logic in a route handler, add it there.

The poll interval is **adaptive**: `POLL_FAST_MS` (2s) whenever the account holds an open position or a working order, `POLL_IDLE_MS` (15s) when it's flat, since nothing can change then without the user acting. It's a self-rescheduling `setTimeout`, not `setInterval`, so the delay is re-evaluated after each tick; a store subscription also re-arms it early when activity appears between ticks.

### Undo/redo (unified history)

`src/lib/history/index.ts` defines a single `UnifiedHistoryStack` (`unifiedHistory`) recording three op kinds: `drawing`, `chartState` (indicator/config/visual changes), and `viewport`. Mutations that should be undoable go through it. Guard against re-recording during replay with `withoutHistory()` / `isApplyingHistory`. Note `src/lib/drawings/history.ts` also exists (drawing-specific); `src/lib/history/` is the newer unified layer.

### Drawing tools

All chart drawings (trendlines, fibs, rays, channels, long/short positions, horizontal/vertical lines, price/date ranges, rectangles, brush) live in `src/lib/drawings/` and `src/components/chart/drawings/`. They are:

- Rendered as an **SVG overlay** on top of lightweight-charts (`DrawingsLayer.tsx`), **not** via the Primitive API.

  Which is why a drag has to drive the crosshair by hand. `beginPointerDrag` takes pointer capture, so every `pointermove` is retargeted to the overlay and the canvas underneath sees nothing: lightweight-charts' crosshair froze where the drag began, and the price axis went on showing the price the gesture *started* at while a stop or an entry was being placed. `aimCrosshairAt()` ([src/lib/chart/crosshair.ts](src/lib/chart/crosshair.ts), the same registry pattern as the viewport applier and `nudge.ts`) is called from the drag's move handler, so this is fixed for every drawing at once — don't re-fix it per tool.
- Stored in `src/lib/store/drawings-store.ts`.
- Persisted to Supabase table `user_drawings` (one row per drawing, `data JSONB`, `kind` discriminator).
- Mutated only through actions that push to the undo/redo history.

The data model is a **discriminated union** by `kind`. All operations (render, hit-test, drag, serialize) `switch (drawing.kind)`. Coordinate ↔ price/time conversion helpers live in `src/lib/chart/coords.ts` and `snap.ts`; shared drag logic in `use-drag-point.ts` / `use-drag-shape.ts`.

**Magnet.** The snap is two modules on purpose. [src/lib/chart/snap.ts](src/lib/chart/snap.ts) is pure and tested: `snapToOHLC` (nearest candle level) plus `drawingPriceLevels`/`snapToLevels`, which also expose what *other* drawings offer at a given time — fib ladders expanded to prices, a channel's two rails, a trend line interpolated to that bar, a long/short's entry/stop/target. [src/lib/chart/magnet.ts](src/lib/chart/magnet.ts) is the thin store-aware wrapper every UI path actually calls (`magnetSnap`, or `magnetSnapDragging` from a drag handler). Two rules when touching it: filter the store's drawings to the charted symbol (`drawings-store` holds every symbol's), and pass the dragged drawing's id as `excludeId` — a shape that can snap to its own levels sticks to where it started and never moves. New snap call sites go through `magnet.ts`, never `snapToOHLC` directly.

**The magnet has two strengths, and they are TradingView's, verbatim.** *Strong* "pulls the drawing points to chart values (bars), regardless of the distance between the points and chart values"; *weak* "pulls the drawing points to chart values (bars) when you are drawing near them". They are a **setting the user picks** (`magnetStrength` on `chart-store`, default `strong`, chosen from the chevron beside the magnet button or from the mobile drawings sheet), not a single behaviour to be tuned. This repo shipped three rounds of tuning one hybrid and was told each time that the magnet was broken — correctly, because a weak magnet reads as *dead* to someone who wanted strong, and a strong one reads as a *teleport* to someone who wanted weak. There is no setting of one number that satisfies both.

Mechanically it is still two gates, but only one of them is now in question. Horizontally the bar's own **column** decides *which* candle: anywhere in it, at any height, aims at that bar, and the only thing that declines is a time more than half a bar outside it — so the strong magnet still lets the cursor move freely in the empty space past the last bar. Vertically, `snapToOHLC`'s optional `maxDistance` is the whole difference: the weak magnet passes `MAGNET_RADIUS_PX` (measured from the candle's **high–low span**, not from its four levels — measuring from the levels is what made it feel dead, since the middle of a long wick is too far from either end), and the strong magnet passes nothing. Unbounded, a bar's wick is a few pixels of a phone's ~500px plot, so a finger aiming at empty space is pulled 147px to that bar's extreme: that is the strong magnet working, not failing. Inside a bar's column the strong magnet drops the reach for **every** candidate, not only the candle's: the target is simply the nearest level there is. Bounding the drawings' and indicators' levels while the candle went unbounded was tried first and is wrong, because the two rules meet at the edge of the reach — a level 48px away drops out and the bar's high, 111px away, wins instead, so one pixel of movement throws a dragged line across the pane and the next pixel throws it back. A magnet has to be monotone in the aim. Outside a column there is no candle, and the reach comes back under both strengths — that is what keeps a horizontal ray's level from grabbing the cursor out of the empty space to the right of the series.

**The puck is on your finger; the crosshair is on the snap.** This is TradingView's mobile model, taken from a recording of its app, and it is what makes a strong magnet legible rather than broken. A white puck (`puckRef` in `PriceChart`, moved imperatively — a React render per touch move is what made the crosshair lag once before) tracks the finger 1:1 and never snaps, for every touch gesture: placing a point, and dragging a drawing through the `aimCrosshairAt` registry. `placeCrosshair` then aims the chart's own crosshair, and therefore its price-scale label, at the **snapped** price and the snapped bar — so the axis reads the price the point will actually take. Aiming the crosshair at the raw finger instead, which is what this did, left the axis quoting a price the point was never going to land on and left nothing on screen moving with the drag: the gesture read as frozen even while it was working correctly. Both halves matter, and a measurement of one without the other proves nothing — `puck.cjs` pins the puck to the finger, `puckshot.cjs` holds a finger in the empty top of the pane and prints puck, magnet target and landed price, which must be the finger, a level, and that same level. A phone's magnet question is usually this one, not the snap maths.

**Dragging a drawing with the magnet on is sticky, and that is the specification.** TradingView documents this exact symptom under *Cursor lags/jumps while drawing*: "Magnet Mode makes all the movable drawings attach to OHLC values, hence the difficulties with moving the cursor", and its remedy is the magnet button or Ctrl/Cmd, not a gentler magnet. So a line hopping between the levels of the column it is over is the feature; what is *not* allowed is the hop being non-monotone or landing further from the finger than a nearer candidate — that is the bug the paragraph above describes. `raymove.cjs` in the scratchpad measures a 150px drag and prints every position the line takes, which is the way to tell the two apart. Note the phone has no Ctrl: the drawing-tools sheet's magnet row is the only escape there.

**It also snaps to the price pane's indicators**, which TradingView added to its magnet in March 2025. [src/lib/chart/indicator-levels.ts](src/lib/chart/indicator-levels.ts) is a registry in the same shape as the viewport applier and the crosshair aimer: the focused chart publishes a function from a time to the values of its visible overlays, and `magnetSnap` adds those to the candidates whenever `magnetIndicators` is on. Two things are deliberate. The arrays are captured in `updateEMAs`/`updateVWAP`, where the study is computed, **not** read back with `ISeriesApi.data()` — that rebuilds its array on every call and this is asked on every pointer move, times however many studies are on. And `valueAtTime` matches a time exactly rather than interpolating: these arrays are computed per candle from the same bars, so a time they lack is off the end of the study (an EMA has no value for its first `period` bars), and inventing one would snap a point onto a line that is not drawn there. Only main-pane overlays belong in the registry — a sub-pane study is drawn against its own scale, so its "price" is not one.

**Ctrl/Cmd inverts the setting; it does not add to it.** TradingView: "You can temporarily turn the strong magnet feature on by [...] holding CTRL/Command", and "if the magnet mode is on you can temporarily turn it off by holding CTRL/Command". So with the magnet off the key gives you the **strong** one for that gesture, and with it on the key gives you a free point — which the old `ev.ctrlKey || magnetMode` spelled out at six call sites and could not express at any of them. `magnetFor(ev)` in [src/lib/chart/magnet.ts](src/lib/chart/magnet.ts) is the single answer to "is the magnet on for this gesture, and how hard"; every snap call site asks it, and a new handler that reimplements the `||` silently loses the off half. `src/lib/chart/magnet-strength.test.ts` pins the truth table and both strengths; `strength.cjs` and `mobstrength.cjs` in the scratchpad measure them over a live chart, desktop and phone.

**Whether a drag snaps depends on whether the grab point is on the level being moved.** The magnet snaps *points*: a new one being placed, or an anchor being dragged (`use-drag-point`, and the long/short's entry/stop/target), each of which resolves to an absolute snapped price. `use-drag-shape` moves a whole shape by a *delta*, and there the price under the cursor is only the right thing to snap when the body you grabbed **is** the level — a horizontal line or ray, which therefore pass `grabIsOnLevel`. For every multi-point shape it is not: you grab a trend line, a rectangle or a long/short box wherever you happen to click, so snapping the cursor moves the shape by the distance from an arbitrary grab position to a candle level. Snapping just the live end of the delta threw the shape by ~40px on the first pixel of every drag and dragging it back did not restore it; snapping both ends instead froze a vertical drag inside one bar's column. Both were nearly invisible while the magnet needed proximity, and constant once a bar owned its whole column. A new shape that opts in needs the grab to lie on the moved price, not merely near it.

**Style defaults vs templates.** `toolDefaults[kind]` is the single "last style used", applied silently to new drawings; `drawingTemplates[kind]` are named presets applied on demand. Editing a style from `FloatingContextToolbar` merges the touched field into `toolDefaults` as a side effect, which only ever captures that one field — the toolbar's pin button (`SaveAsDefaultButton`) copies the drawing's whole style at once via `styleOf()`, and `clearToolDefault(kind)` (in the templates menu) drops it. `styleOf`'s `STYLE_FIELDS` list is the single definition of "what counts as style"; fib `levels` are in it deliberately, since carrying a customised ladder to the next fib is the point.

### Anchored VWAP

`src/lib/indicators/vwap.ts` is a **port of the trade journal's VWAP** (`workers/trade-journal-worker/src/indicators.js` in the `kisushotto-site` repo), kept numerically identical on purpose so the same symbol reads the same in both apps — including the journal's palette (`#3b6cf6` mean; `#2fa84f` / `#e3c430` / `#e5484d` for 1σ / 2σ / 3σ). If the journal's formula changes, change it here too.

Two things about it are deliberate and easy to "fix" by mistake:

- **The NY anchor resets twice a day.** `anchorKeyFor("ny")` gives pre-market bars their own segment, so a session breaks at local midnight *and* again at 09:30. That is the journal's behaviour (`minutes >= 570 ? date : date-pre`), replicated rather than corrected.
- **Session joins are drawn transparent.** A line point's colour paints the segment running to the *next* point, so the last bar before a reset gets `color: "transparent"`. Without it the chart draws a diagonal from where one session ended to where the next begins, which reads as a real price move.

The timezone lookup is cached per UTC hour. The journal calls `Intl.formatToParts` once per candle, which is fine for a ticket chart's handful of bars; here the same code runs over up to 2000 candles on every WebSocket tick, where it would be far too slow. DST is still followed exactly — a fixed offset would not be.

### Alerts

Two independent mechanisms feed one evaluator:

- **Drawing-attached alerts** — the `.alert` field on `hline`/`hray`/`trendline`/`ray` drawings, synced to Supabase along with the rest of the drawing (see above).
- **Standalone alerts** (price / RSI / MACD) — `alerts-store.ts`, localStorage-only.

Both are evaluated together in [src/hooks/useAlertMonitor.ts](src/hooks/useAlertMonitor.ts), mounted **per-symbol inside `PriceChart`** (not globally in `providers.tsx`) and driven off the live last-price tick, so an alert only fires while its symbol's chart is open. Crossing detection (`conditionHit`/`priceLevelFor` in `src/lib/alerts/alert-eval.ts`) compares the previous vs current tick; sloped drawings (trend line / ray) are interpolated to the current bar's time so a moving price can cross a projected line. A 30s per-alert cooldown avoids duplicate toasts on a chattering price. Firing pushes to `alerts/toast-store.ts` (rendered by `AlertsToast.tsx`, mounted once in `providers.tsx`) and optionally plays a sound (`alerts/sound.ts`).

### Trading (live Binance + Bybit orders)

The user picks an exchange and enters API key/secret in the UI (`trading-store.ts`, persisted). Everything private goes through `src/app/api/trade/*`, which signs server-side and forwards to the venue. Credentials are passed per-request in the body/query — they are **not** stored server-side.

Each route takes an `exchange` param and dispatches: Binance is signed inline (HMAC-SHA256 over the query string), while Bybit lives in [src/lib/exchanges/bybit.ts](src/lib/exchanges/bybit.ts) (V5 scheme: `HMAC(timestamp + apiKey + recvWindow + payload)` with `X-BAPI-*` headers). That module also holds **pure mappers** normalizing Bybit responses to the shared `Order` / `Position` / `AssetBalance` shapes, which is where its tests live. Adding an exchange means extending `Exchange`, the per-route dispatch, and a mapper module.

Two venue differences leak into the shared model and are easy to get wrong:

- **TP/SL attachment.** Binance always expresses them as separate `reduceOnly` orders. Bybit stores them *on the position* (`takeProfit`/`stopLoss`): `placeOrder()` attaches them directly to a brand-new entry order's `/v5/order/create` call (`bybitPlaceOrder`'s `takeProfit`/`stopLoss` args) so the position gets its native TP/SL from the moment it opens, while editing an *already-open* position's TP/SL goes through the Bybit-only `/api/trade/trading-stop` route (`bybitSetTradingStop`) instead — two different Bybit endpoints for what looks like the same UI action, depending on whether a position exists yet. `Position` carries optional fields for both, and UI prefers the position's own values, falling back to matching reduceOnly orders (always for Binance; for Bybit only orders placed before this native-attach path existed). A position's stop can therefore surface twice (as a position field *and* an order) — the chart overlay deliberately skips orders a position already draws.
- **Hedge mode.** Bybit rejects orders whose `positionIdx` doesn't match the account's position mode (0 one-way, 1 hedge-long, 2 hedge-short). `Position.positionIdx` is plumbed through so TP/SL edits, closes, and new orders send the right index. Inferring hedge mode from *currently open* positions goes blind while flat (no positions ⇒ nothing to inspect) — `bybitIsHedgeMode()` (`/api/trade/position-mode`) queries `/v5/position/list` directly instead, since Bybit keeps returning a hedge-mode symbol's two dormant size-0 rows even with no position open.

A TP/SL's displayed P&L is signed by direction, via `pnlAtExit()` in [src/lib/trading/sizing.ts](src/lib/trading/sizing.ts) — never `Math.abs` plus a fixed sign per bracket kind. A stop trailed past the entry (above it on a long, below on a short) locks in a gain rather than capping a loss, and the number has to say so; the same holds for a target dragged to the wrong side. It takes the **position's** side, not the reduceOnly order's — that one points the other way and inverts every sign.

`Position.percentage` is the true **ROI** (`unrealizedPnl / initialMargin`), not a naive price-delta × leverage estimate — those diverge, and even flip sign, once margin is added or the account is on cross. The chart's entry line intentionally shows *price movement* instead, matching TradingView; the positions table shows the ROI.

**Route auth — read before adding anything under `/api/trade/`.** These routes sign requests against a real exchange, so an unauthenticated caller must never reach them, or the deployment becomes an open proxy a stranger can point at their own keys on our Vercel quota. That gate used to be the proxy matcher; it is now `requireSession()` ([src/lib/supabase/require-session.ts](src/lib/supabase/require-session.ts)), called as the **first statement of every handler**. On Vercel the proxy runs as its own Function, so the old arrangement billed two invocations per request — which on a 2s account poll is the whole cost. Same JWT check, half the invocations. The trade-off is that the matcher no longer covers the prefix by default: **a new handler that forgets the guard is wide open.** `exchange-info` is the one deliberate exception (public symbol metadata, no credentials, CDN-cached). `src/proxy-matcher.test.ts` pins down what the matcher does and does not run on.

**Exchange gating:** account data always comes from the single connected exchange, but the chart may be showing a different venue's symbol. UI that overlays account state (chart order lines, watchlist position badges) must check `resolveSource(symbol).kind === tradingExchange` before rendering, or a Bybit position leaks onto a Binance chart of the same ticker.

Order sizing/risk math is pure and tested in [src/lib/trading/sizing.ts](src/lib/trading/sizing.ts). Canonical state is `qty` (base asset); every other display value is derived. Two distinct concepts share the word "risk" and must not be conflated: `SizingMode.RISK_USD`/`RISK_PCT` size the position *from* a risk budget and the stop distance, whereas `SlMode` only expresses *where* the stop sits (`PRICE` / `PCT_PRICE`). Risk is deliberately not an `SlMode`, since risk-on-both-sides is circular.

Per-symbol tick/lot precision (`pricePrecision`, `stepSize`, `minNotional`, …) comes from `useSymbolInfo()` ([src/lib/trading/symbol-info.ts](src/lib/trading/symbol-info.ts)), a client-cached wrapper around `/api/trade/exchange-info`. Anywhere a price gets rounded — a typed input, a bid/ask click, or a chart-line drag — must use this precision rather than a fixed decimal count: a hardcoded `.toFixed(2)` silently breaks sub-$1 symbols that need more decimals just to move the price at all.

Chart-side trading UI is in `src/components/trading/`. `OrderLinesLayer.tsx` draws entry/TP/SL/liquidation as an SVG overlay **plus** native lightweight-charts price lines — the native ones give the colored price-scale label and span the full pane (so a line continues past the SVG chip toolbar), and they're kept in sync with any in-progress drag so a dragged level doesn't leave a duplicate behind. Position TP/SL edits are two-step: drag → `pending` → explicit Confirm/Discard on the entry line before anything is sent. Right-clicking a position's TP/SL line opens a small menu ("Modify order…" / "Remove") instead — Modify calls `trading-store`'s `openPositionEdit()`, which stashes the position in `editingPosition` and switches the right sidebar / mobile shell to the Trade tab; `OrderPanel` renders `PositionEditPanel` (a typed price + ticks form) in place of the normal order form whenever that's set, so a price can be typed instead of dragged.

A working order's price/quantity can be edited either from the chart (drag its line) or from the Orders table ([src/components/layout/PositionsPanel.tsx](src/components/layout/PositionsPanel.tsx)'s edit popover) — both go through `modifyOrder()`, which cancels and re-posts with the given overrides since neither exchange supports an in-place amend. Leverage lives on the symbol/account, not the order, so editing it from that same popover calls `setLeverage()` separately and affects any future fill on that symbol, not just the order being edited.

### Chart layouts (multi-chart grid)

The chart area is a grid of 1, 2, 3 or 4 charts, each with its own symbol and timeframe, picked from the header's `LayoutSelector`. [src/lib/chart/layouts.ts](src/lib/chart/layouts.ts) is the dependency-free leaf module holding the layouts and the pane reconciliation (`chart-store` needs the pane count and the picker needs the labels, so it must import neither); `ChartGrid.tsx` renders one `PriceChart` per pane.

**`symbol` and `timeframe` on the store are the *active pane's*, mirrored.** Everything else in the app — the watchlist, the trading panels, the alert dialog, the drawing store's filtering — reads those two fields and must keep working untouched, so `setSymbol`/`setTimeframe` write both the mirror and the focused pane, and `setActivePane` re-mirrors from the pane it focuses. A single-pane layout is therefore exactly what the app was before: `ChartGrid` renders a bare `PriceChart` with no focus ring and no click-to-focus.

**Exactly one pane owns the app's single-slot state.** `PriceChart` registers global capabilities whose registries hold one callback each — `candlesRef` (read by `BarCountdown` and the snapshot composer), `registerViewportApplier`, `registerChartCapture`, `registerPricePerPixel`, `registerCrosshairAimer`, `markChartTick()` — and mounts `useAlertMonitor`. With four charts up, the last one to mount would otherwise win every registry and the keyboard/undo/snapshot paths would act on an arbitrary chart. The `active` prop (default `true`, so mobile's `ChartScreen` and the single-pane case need nothing) gates all of them; an inactive pane still draws, streams and can be drawn on, it just does not claim the slots. Anything new that registers globally from `PriceChart` has to go through the same gate, or a four-pane layout silently points it at the wrong chart.

**Focus follows a press in the capture phase.** The chart swallows pointer events for its own crosshair and drawing handling, so a bubbling listener on the cell would never see a press that landed on the canvas — which is every press that matters. The focused cell is marked with an inset `box-shadow` ring rather than a border: a border would change the cell's content box, so focusing a pane would resize its chart and make the grid twitch as you click between them.

**Reconciliation is a pure function because of how Zustand's `merge` works.** `reconcilePanes` must be handed the *persisted* panes, never the merged ones. Zustand lays the persisted state over the defaults, so a user who last used a build without layouts arrives with the **default** pane sitting in the merged object; seeding from that hands them `BTCUSDT`, and the active-pane mirror then overwrites the symbol they actually had saved. It is the one piece of persisted state whose length must agree with another field (`layout`), and a layout saved on one device can arrive at a build that no longer has it, so the list is rebuilt to exactly the length the layout needs on every rehydration. Covered by [src/lib/chart/layouts.test.ts](src/lib/chart/layouts.test.ts).

Layouts are desktop-only for now: `MobileShell`'s chart screen renders a single `PriceChart`, as the phone apps do. Every layout here is a uniform grid; an asymmetric arrangement (one tall chart beside two short ones) would add a per-cell template to `LayoutSpec` rather than special-casing the grid in the component.

### Bar close countdown

The chip counting down to the current bar's close sits on the price axis, under the last-price label — lightweight-charts has no API for annotating the price scale, so `BarCountdown.tsx` is an absolutely-positioned overlay that derives its own geometry the way every other overlay here does: `timeScale().width()` for where the plot ends and the axis begins, `priceToCoordinate(lastPrice)` for the label's y. It reads the last bar off the shared `candlesRef` (WS ticks mutate that array in place, so a 1s re-read always sees the live bar) and is gated on `showBarCountdown`, so the interval isn't paid for when the chip is off.

The plate carries the price, the change and — only when the countdown is switched on — the time to the close, and it stands in for lightweight-charts' own last-value label (`PriceChart` turns that off while it is mounted) rather than sitting under it.

**It is fixed on its price and yields when covered.** The crosshair's own price label is drawn across it whenever the cursor passes the last price, and the plate used to *dodge* — a whole block height, signed away from the crosshair. That kept both readable and broke what a price axis is for: the last price left the price it belongs to, so it appeared to jump around the scale whenever the cursor came near. It now stays put and unmounts while the crosshair's label is over it (`covered`, from a `subscribeCrosshairMove` handler), so the price under the cursor has priority — that is the one being read. Because the plate no longer moves, the overlap test is taken against one fixed position and there is no feedback loop to oscillate, which the dodging version had to be written carefully to avoid.

The close time itself is [src/lib/chart/countdown.ts](src/lib/chart/countdown.ts). `barCloseTime` special-cases `"1M"` with real UTC calendar arithmetic: `timeframeToSeconds("1M")` is a 30-day approximation that's fine for pixel math but would drift the clock by up to a day and a half.

### Chart snapshots

`chart.takeScreenshot()` only paints lightweight-charts' own canvas, so it would
drop every annotation — drawings and order lines are SVG overlays stacked on
top. `composeChartPng()` ([src/lib/chart/snapshot.ts](src/lib/chart/snapshot.ts))
composites the two, scaling the CSS-pixel overlays up to the canvas's
device-pixel size and inlining `var(--token)` colours (serialized SVG leaves the
document, so those would otherwise resolve to black). PriceChart registers the
capture through the same registry pattern as the viewport applier.

Snapshots upload to the **public** `snapshots` Storage bucket
(`supabase/migrations/04_snapshots.sql`) under a `<uid>/` prefix: writes are
owner-only via that prefix, reads are public because the point is a URL that
renders in an external journal. Clipboard image copy hands `ClipboardItem` the
*promise* rather than an awaited blob — Safari drops the user-gesture permission
across an `await`.

### Auth & cloud sync

`src/proxy.ts` (Supabase SSR) gates the whole app: unauthenticated users are redirected to `/login` (except `/login` and `/auth/*`). It checks the session with **`getClaims()`**, which verifies the JWT locally, not `getUser()`, which round-trips to Supabase's auth server on *every* request — at one proxy run per request that round trip dominated the billed wall-clock of the whole app. Any error or exception is treated as unauthenticated, so a failure redirects to `/login` rather than opening the door. On sign-in, `useCloudSync` + `useDrawingsSync` load the user's chart settings, watchlist, and drawings from Supabase, then debounce-save changes back. Supabase clients: `client.ts` (browser), `server.ts` (route handlers / proxy). Schema + RLS policies in `supabase/schema.sql` and `supabase/migrations/`.

**The file is `src/proxy.ts`, not `middleware.ts`.** Next.js 16 deprecated the `middleware` file convention and renamed it to `proxy` (`v16.0.0`: "Middleware is deprecated and renamed to Proxy. Proxy defaults to the Node.js runtime"). The exported function must be named `proxy`, the `config`/`matcher` shape is unchanged, and `runtime` is **not** configurable in a proxy file — setting it throws. There is a codemod (`npx @next/codemod@canary middleware-to-proxy .`) if the rename ever needs redoing.

The `matcher` is also a **billing** control, not just an auth one: a matched request runs the proxy as its own invocation *before* the CDN cache is consulted, so a matched path can never be served purely from cache however long its `Cache-Control` is. The public data proxy routes (`/api/yahoo`, `/api/fred`, `/api/coingecko`) are therefore excluded — they return identical credential-free market data to everyone and set long `Cache-Control` headers so Vercel's CDN answers repeats with no function run at all. All of `/api/trade/` is excluded too, including `exchange-info`, which is the one that really matters for CPU: it parses a multi-MB Binance `exchangeInfo` document to pluck a single symbol. The signed routes under that prefix are protected by `requireSession()` instead (see "Route auth" above), *not* by being unprotected. Adding a new public, cacheable proxy route means adding it to the matcher exclusion too, or the cache headers do nothing.

### Trade journal integration

The **trade journal** (`trade-journal/` + `workers/trade-journal-worker/` in the `kisushotto-site` repo) is a separate app on Cloudflare Workers that owns the trading rules, the ledger, the sealed API-key vault and a cron **guardian** that closes or flags positions breaking the rules. Its `risk.js` states the invariant this integration has to respect: *"el servidor es el que dice si una orden sale o no; nada del navegador es confiable."*

**Stage 1 — read-only — is what exists today.** `JournalPanel` (the right sidebar's Journal tab) polls the gateway's `GET /exec/status` through [src/hooks/useJournalStatus.ts](src/hooks/useJournalStatus.ts) and renders the verdict the gateway already reached. It cannot place, move or cancel anything. Execution still goes through this app's own `/api/trade/*`.

Three things to know before extending it:

- **The request goes browser → Worker, never through a Next.js route.** The Worker sets `Access-Control-Allow-Origin: *` and accepts `Authorization`, so proxying it here would add a Vercel Function invocation per poll and buy nothing. This is also why the poll is free: it never touches Vercel.
- **Auth is the journal's own JWT** (`tj_jwt`). `charts.kisushotto.com` is a different origin from the journal, so localStorage does not carry over and the panel asks for the token to be pasted. A 401/403 latches the poll off rather than hammering the Worker.
- **Rule verdicts are read, never recomputed.** [src/lib/journal/gates.ts](src/lib/journal/gates.ts) flattens whatever `status.gates` contains without naming individual rules, so a rule added in the journal appears here with no change on this side. Do not port the rules engine over: two copies drift, and the browser copy is the one `risk.js` says not to trust.

**Stage 2, when it happens, must delete `/api/trade/*` in the same commit that starts calling `/exec/order`.** While both paths exist there are two doors to the exchange and only one has the guardian behind it — and a guardian with a known bypass is not a guardian. The gateway's `POST /exec/preview` is the same `order()` with `dry = true`, so the order panel can show the server's verdict live before anything is sent.

### Responsive shell

`src/app/page.tsx` branches on `useIsMobile()`: desktop renders the full sidebar/panel layout; mobile renders `MobileShell` (bottom-tab screens in `src/components/mobile/`). The dialog components are shared across both.

Mobile screens are being brought to feature parity with their desktop equivalents screen by screen (an ongoing effort — not every screen is there yet). The pattern: call the *same* Zustand store actions desktop uses (no parallel mobile-only state), reserve `mobile-store.ts` for navigation only (current tab, which fullscreen sheet is open), and reuse `MobileSheet` for anything desktop shows in a dropdown/popover/dialog. Only the *interaction* is touch-adapted, not the underlying behavior: desktop's native HTML5 drag-and-drop becomes a `setPointerCapture` + manual hit-testing implementation (touch browsers don't reliably fire `dragstart`/`drop`), and desktop's right-click context menu becomes a long-press (a `pointerdown` timer cancelled on `pointermove` past a small slop or on `pointerup`) opening the same actions in a sheet. A drag handle or a long-press target that sits inside a row with its own tap handler must call `stopPropagation()` on every pointer event it handles (down/move/up/cancel) — pointer capture keeps routing events to it, but they still bubble to the row's handlers unless stopped, so a button tap would otherwise also fire the row's tap-to-open. `WatchlistScreen.tsx` is the fullest example of this pattern so far. `TradeScreen.tsx` goes one step further and imports `matchTpSl`/`EditOrderPopover` directly from the desktop `PositionsPanel.tsx` (both exported for this) rather than reimplementing them — `EditOrderPopover` in particular needed no touch adaptation at all, since it's already a centered modal rather than a hover-dependent popover.

Some desktop-only pieces already work on mobile with zero extra code, because they're mounted inside components mobile already renders unchanged: `FloatingContextToolbar` (per-drawing delete/duplicate/lock/style) and the indicator pill row (hide/remove/settings, including per-instance EMA settings) both live inside `PriceChart.tsx`, which `ChartScreen.tsx` renders as-is; the indicator/chart-settings/drawing-settings/create-alert dialogs are mounted directly in `src/app/page.tsx`'s mobile branch alongside `MobileShell`, "reusing the desktop dialogs" per the comment there. Check for this kind of free reuse before porting a feature — `MobileDrawingsSheet.tsx` and `MobileIndicatorsSheet.tsx` only needed to add the *triggers* (favorite star, magnet/alert/clear rows, "add EMA") that desktop exposes via right-click or a sidebar button mobile has no equivalent gesture for; the tool catalog itself is imported from the desktop-owned `drawing-tools.ts` rather than duplicated, so a tool added there appears on mobile automatically.

Not every desktop panel is safe to reuse as-is, though: `AlertsPanel.tsx`'s edit/delete buttons are hover-revealed (`opacity-0 group-hover:opacity-100`), which never becomes visible on touch, so `MobileAlertsSheet.tsx` reimplements the same two lists (standalone + drawing-attached alerts) with always-visible actions instead of importing the panel directly — check whether a component's interactive affordances *depend* on hover before reusing it wholesale, not just whether its layout would fit. Its "+" (create alert) button calls the same `openAlertDialog()` a desktop right-click on the chart uses; `CreateAlertDialog` itself needed no changes since it's a centered modal, not a hover-dependent popover, and mobile's `page.tsx` branch already mounts it. Desktop's `ChartTypeSelector` and `SnapshotButton`, by contrast, *are* directly reusable — they're built on the shared `DropdownMenu` primitive (Base UI, tap-triggered and portal-rendered, so it doesn't clip against `ChartScreen.tsx`'s horizontally-scrolling toolbar) — `ChartScreen.tsx` imports both as-is. `TimeframeSelector` is the opposite case again: a hand-rolled `absolute`-positioned dropdown with its own hover-revealed favorite star, so `MobileTimeframeSheet.tsx` reimplements it as a fullscreen list instead. The lesson each time: check whether the desktop piece is built on the shared portal-based `DropdownMenu`/dialog primitives (safe to reuse) versus hand-rolled positioning or hover-only affordances (needs a mobile-specific rebuild) — don't assume either way from layout alone.

**A hand-positioned popover has to be placed against the viewport, not against its trigger.** `ColorPicker`'s palette was `absolute right-0 top-full`, which is fine on a desktop and off the screen twice over on a phone: the drawing toolbar sits near the bottom of the chart because that is where a thumb reaches, so a 280x330 panel opening downwards ran off the bottom edge, and right-aligning it to a swatch near the left ran off the other side. It now renders in a portal on `document.body` as `position: fixed`, positioned by `placePopover` ([src/lib/ui/popover-position.ts](src/lib/ui/popover-position.ts), tested) — prefer below, flip above only when below does not fit *and* above fits better, then clamp both axes. The portal also takes it out of any ancestor that clips, which is what lets the toolbar scroll. Two things a portal breaks if you are not careful and both are covered by `palettedialog.cjs`: it must sit above the settings dialogs that embed it (`z-[60]` against their `z-50`), and a click inside it must not read as a click outside them.

**The drawing toolbar is capped at the chart's width and scrolls.** At touch size every control is 32px, and a long/short carries three colour pickers, seven actions and the limit-order button — more than a phone is wide, so clamping its position could not help: a clamp only moves something that already fits. `FloatingContextToolbar` sets `maxWidth: containerSize.width` and puts everything but the drag handle in a `no-scrollbar overflow-x-auto` row, the same way the mobile chart toolbar works. Its segments and separators are `shrink-0`, or the row squashes instead of scrolling.

**Reusing a hover-dependent panel: ask `(hover: none)`, not the width.** `AlertsPanel` was rebuilt for mobile because its controls were `opacity-0 group-hover:opacity-100`. `ObjectTreePanel` had the same problem and did *not* need a rebuild — adding `[@media(hover:none)]:opacity-100` beside the existing `group-hover` class reveals those controls on a touch device while a narrow desktop window, which hovers perfectly well, keeps the reveal-on-hover behaviour. Prefer that to a second implementation: two lists of the same drawings drift. `MobileObjectsSheet` and `MobileJournalSheet` both just wrap the desktop panel in a `MobileSheet`.

**The mobile chart's layout follows TradingView's, deliberately.** The toolbar is at the **bottom**, under the chart and above the tab bar: on a tall phone the top of the screen is the one place a thumb cannot reach without shifting grip, and moving it down also hands the chart the full height. Its ordering is the reachability contract — the bar scrolls horizontally (with the scrollbar hidden, since it is swiped), so symbol, timeframe, drawing, indicators and objects sit before a divider and chart type, undo/redo, replay and snapshot after it. There is no separate header, because `PriceChart`'s own legend line already carries symbol, timeframe, venue, price and change.

A few mobile-only behaviours live inside otherwise-shared components, keyed off `useIsMobile()`: `IndicatorPill` collapses its three action buttons until tapped (carrying them always cost about a third of the plot width *per study*), the legend wraps and drops the venue and volume while a candle is being read, and the price pane's stretch goes from 3 to 5 so it keeps ~71% of the height. That last one is re-applied from its own effect — `useIsMobile` is `false` on the first render by design, so the sub-pane effects have already run with the desktop value by the time it resolves.

**`useIsMobile` is not just a width check.** A phone held sideways is ~915 x 412, which clears the width breakpoint and used to drop the user into the full desktop shell — the opposite of what rotating a chart asks for. The hook also matches a short viewport, gated on `(pointer: coarse)` so a short *desktop* window keeps the desktop layout.

**A touch long-press is not a right-click.** The browser raises `contextmenu` from the same gesture lightweight-charts uses to summon the crosshair, so the chart's "Add alert here" menu opened on every attempt to read a price. `PriceChart` records the last `pointerType` and skips its menu for touch and pen, while still calling `preventDefault` to suppress the browser's own callout. Any new context menu over the chart needs the same guard.

Known remaining gap: the mobile shell has no equivalent of the desktop status bar (`BottomPanel`); the feed indicator it carries is mirrored as a dot in the chart legend, but the 24h statistics are not surfaced anywhere on a phone.

### Typography

The app leans heavily on very small arbitrary text sizes (`text-[9px]`…`text-[12px]`). [src/app/globals.css](src/app/globals.css) overrides these **globally**, enforcing an 11px floor, and also raises Tailwind's `--text-xs`/`--text-sm` tokens. The overrides are declared *unlayered* (outside `@layer`) so they beat Tailwind's generated utilities regardless of source order. So a `text-[10px]` in a component does not render at 10px — change the sizing scale there, not per-component, and verify against the compiled CSS.

SVG overlays (chart drawings, order lines) size text with the numeric `fontSize` attribute instead, which those CSS rules do **not** affect — they must be adjusted in the components themselves.

## Keyboard shortcuts

Centralized in `src/hooks/useKeyboardShortcuts.ts`. The chart-level handler is global (`window`), guarded against input elements.

| Key | Action |
|---|---|
| `Esc` | Cancel current placement → reset tool → deselect |
| `Ctrl+Z` / `Cmd+Z` | Undo |
| `Ctrl+Shift+Z` / `Ctrl+Y` | Redo |
| `Del` / `Backspace` | Delete selected drawing |
| `←` `→` `↑` `↓` | Nudge selected drawing (`Shift` = 10x) |

Mouse gestures on the chart live in `PriceChart.tsx`'s own `dblclick` handler rather than that hook. Double-click resolves in priority order: an EMA or key-level line within a few pixels opens its settings; a sub-pane opens its indicator's settings; otherwise, on **empty main-pane background with nothing selected and no placement in flight**, it collapses/restores the indicator sub-panes (`subPanesHidden`), the way TradingView maximizes the price pane. The "nothing selected" guard is what keeps a double-click that was really a deselect from silently hiding every study, and the handler ignores clicks past `timeScale().width()` so lightweight-charts keeps its own double-click-to-reset behaviour on the price scale.

Arrow nudging translates via the pure `translateDrawing()` (`src/lib/drawings/translate.ts`) and follows the drag convention — `updateLive` per keypress, one `commit` once the run settles — so holding a key doesn't spam history or the cloud. Vertical steps are one screen pixel, which the hook gets from a probe `PriceChart` registers in `src/lib/chart/nudge.ts` (same registry pattern as the viewport applier), since only the live chart knows the price-per-pixel scale.
